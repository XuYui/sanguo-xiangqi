# 三人中国象棋（三国象棋）联机对战平台 · SPEC

## 0. 一句话说明

把实物「三国象棋」六边形棋盘电子化，做成**三人实时联机对战**的 Web 应用，
在线体验：<https://chess.xylab.site>。

**当前状态**：棋盘几何、规则引擎、对局状态机、Socket.IO 联机层、账号与持久化、前端界面和生产部署均已实现。
规则变更仍须同步更新 `packages/core/test/`；联机、账号和界面行为分别由 `apps/server/test/` 与 `apps/server/test/click.test.ts` 覆盖。

## 2. 棋盘几何（从实物逆向，已用坐标算死）

- **135 个交叉点** = 3 家 × 9 列 × 5 行；每家 45 点。
- 每家地盘是**扇形**：底线 9 点等分六边形的一条边，越靠中央越宽
  （行内格距 0.125 → 0.197）。
- **列线是直线**；**最内一行（第 5 行）是折线**：`角点 → 自家顶点 → 角点`，
  折角约 133°，顶点正好落在中央三角形的三个顶点上。
- **中央三角形是印刷装饰腔**：内部没有任何线路，棋子永远进不去。
- 六边形顶点处是 90° 直角，棋子不能在那里拐弯。

### 2.1 可通行图（本项目最关键的结构结论）

三家地盘**不共享格线**。跨家连线只发生在三条界河两侧的最内一行（rank 5），
每条界河有 5 对对应点，共 **15 条跨河边**。三对最外端的角点连接是最短的渡口：

```
赤壁（魏|吴，左下）：魏(1,5)  ↔  吴(9,5)
祁山（魏|蜀，右下）：魏(9,5)  ↔  蜀(1,5)
荆州（蜀|吴，上方）：吴(1,5)  ↔  蜀(9,5)
```

三对角点渡口两端的直线距离恰为 **0.1111 = 六边形边长的 1/9**。
其余跨河边也是按几何最近的对应点生成，最长约 0.294，全部已经由拓扑测试断言。

于是：

- 三家最内一行和三对角点渡口构成一条闭合的 **27 步内环路线**；其余跨河边提供同一界河上的对应通道。
- 全图 **135 点 / 243 边**（228 条本家格线 + 15 条跨河），**连通**；
  度数分布：4 度 81 点 / 3 度 45 点 / 2 度 6 点 / 5 度 3 点。
- 当前实现固定使用这 15 条跨河边；源码中没有 `RuleConfig.crossingMode` 切换项。

### 2.2 与象棋的对应关系（走法的统一依据）

每家地盘就是象棋的「半边棋盘」（9 列 × 5 行），三条界河就是象棋的河界：

- **跨河 = 沿列线前进一步**：我方第 5 行第 f 列 ⟷ 对岸第 5 行第 10 − f 列
  （15 条跨河边恰好全部满足这个对应，等同象棋「我方 f 路 = 对方 10 − f 路」）。
- **过河后坐标旋转 180°**：我方「前」= 对方「后」，我方「右」= 对方「左」。
- **中路第 5 列的顶点**（中央三角形的顶点）同时面对两条界河，所以第 5 列「向前」有两个分支，
  中央三角形的三条边就是三家第 5 列的跨河边。
- **行线**：第 2~5 行在第 5 列有折角，但这只是扇形盘的几何变形，与象棋一样仍是同一条横线；
  行线到第 1 / 第 9 列（棋盘边）为止，六边形顶点处不能拐弯。

实现：`board.ts` 的 `stepToward(点, 方向)` 统一负责「沿某方向走一步」（含过河与坐标翻转），
車、炮、馬、相、仕、兵全部建立在它之上。

**玩法后果**：帥只能沿**跨河的同一列线**被照面或被車/炮远程攻击
（例如魏第 4 列 = 蜀第 6 列，魏第 6 列 = 吴第 4 列，第 5 列同时连到两家）。

**③ 帅的落点是所有入射直线的并集（不依赖从哪个方向进入）。**

九宫的格线在 `(5,1)` 处折弯，所以「车从左边来能打到帅」与
「车从右边来能打到帅」是**同一个**关系，不存在方向相关的歧义。

## 3. 棋子与走法（规则已冻结）

三家各 16 枚，摆法为标准象棋半边（`file 1..9` 自该家左手边起，`rank 1` = 底线）：

```
rank 5: ·  ·  ·  ·  ·  ·  ·  ·  ·        第 5 行 = 最内一行（界河走廊）
rank 4: 兵 ·  兵 ·  兵 ·  兵 ·  兵         5 枚兵（file 1,3,5,7,9）
rank 3: ·  炮 ·  ·  ·  ·  ·  炮 ·         2 枚炮（file 2,8）
rank 2: ·  ·  ·  ·  ·  ·  ·  ·  ·         九宫中心（印势力名）
rank 1: 車 馬 相 仕 帥 仕 相 馬 車         底线 9 枚
```

### 3.1 各棋子规则（均按象棋规则映射，见 §2.2）

| 棋子 | 走法 | 关键点 |
|---|---|---|
| **車** | 沿行线或列线滑行，遇子停、可吃第一个子 | 行线贯穿第 1~9 列（中路折角不断开）；列线可跨河接到对岸第 10 − f 列；第 5 列在中央顶点分两路；不能在顶点或渡口拐弯 |
| **炮** | 同車滑行；走子须落空点，吃子必须隔**一个**炮架 | 炮架本身不能吃；架后第一个子才能吃 |
| **馬** | 走「日」：`(±1, ±2)` / `(±2, ±1)`，马腿是长边方向的第一格 | 跨河一步算纵向一步；起点、马腿、落点必须围成完整的 2×1 格块，所以馬的走法可逆，中央顶点处不会拼出假日字；最多 8 个落点 |
| **相** | 走「田」：斜走两格 `(±2, ±2)`，**象眼是对角中点** `(±1, ±1)` | **不过河**；全程只能到达自家 7 个相位，与象棋相同 |
| **仕** | 沿九宫斜线走一格 | 九宫斜线只有两条且都过中心 (5,2)：只有「中心 ⟷ 四角」；斜走没有中间点，不会被阻挡 |
| **帥** | 九宫内直走一格 | 不出九宫 |
| **兵** | 见下 | 三家对称 |

> `packages/core/diagrams/` 里的图由引擎直接计算生成，可直接肉眼核对。

### 3.2 兵的规则（与象棋相同）

1. **未过河（在自家地盘，含自家第 5 行）**：只能向前一步。第 1~4 行是同列 `rank + 1`；
   第 5 行再向前就是过河（中路顶点可选赤壁或祁山一侧）。未过河不能横走。
2. **已过河（在敌家地盘）**：可向前一步（该家 `rank − 1`，朝其底线），也可横走一格（该家同一行）。
3. **永不后退**：对岸坐标是翻转的，所以再走任何一条跨河边（无论是退回自家还是跨到第三家）
   在兵自己的坐标里都是后退，不允许。兵到达敌家底线后只能横走。

**一条完整的进攻路线**（7 步，见 `diagrams/06-兵走法.svg`）：
魏(3,4) → 魏(3,5) → 过赤壁到 蜀(7,5) → 推进 2 → 横走 1 → 推进 1 → 横走 1 抵达蜀家九宫中心。

### 3.3 回合与顺序

- 势力位置与史实一致：魏在下方，**蜀在右上、吴在左上**（赤壁 = 魏|吴，祁山 = 魏|蜀，荆州 = 蜀|吴）。
- 固定顺序轮转：**魏 → 蜀 → 吴 → 魏**（在棋盘上为逆时针：下 → 右上 → 左上）。
- 可**无限过河**（不限制进入别家地盘的次数）。

## 4. 胜负与特殊规则（已冻结）

| 规则 | 采用 | 说明 |
|---|---|---|
| **被将死** | ✅ | 被将死的一方**立即出局**，其棋子全部移除，剩余两家继续；最后存活者胜 |
| **飞将（将帅不得照面）** | ✅ | 三方两两判定：两个帥在同一条可通行直线上且中间无子，则不允许形成该局面 |
| **长将判负** | ✅ | 连续将军达到上限（默认 6 次）判负 |
| **困毙判负** | ✅ | 轮到自己时无任何合法走法 = 判负（象棋规则） |
| **认输** | ✅ | 联机层广播认输事件；认输方出局，剩余两家继续，最后存活者胜 |
| **求和** | 未实现 | 当前消息协议没有求和操作 |
| **超时判负** | 第一版不做 | 已确认推迟（回合计时器留待第二版） |

## 5. 对局功能范围（第一版）

**做**：
- 三人实时联机对战
- 房间邀请码（3~8 位字母数字，服务端创建或加入）
- 账号注册、登录、90 天会话，以及账号绑定的座位恢复
- 观战
- 开局前自由选择魏/蜀/吴座位，三席全满后自动开局
- 所有玩家统一使用魏视角，棋盘不随座位或玩家切换旋转
- 断线重连、进行中对局持久化、聊天、认输

**不做（明确推迟）**：
- AI 对手
- 棋谱复盘 / PGN 导出 / 悔棋
- 对局战绩统计
- 求和
- 回合计时器

代码结构需为这些留出扩展位（引擎纯函数、状态可序列化）。

## 6. 界面约定

- 底图：由 `packages/core/data/board-empty.svg` 生成并复制到 `apps/web/public/board-plain.svg`，棋子用 DOM 叠加。
- `apps/web/public/board-geometry.json` 由 `packages/core/tools/exportWeb.ts` 生成，包含 135 个点的 SVG 坐标；网页固定使用魏视角（0°），不再提供蜀/吴视角切换。
- **必须关掉**底图里的势力名与九宫叉线，否则与棋子/高亮打架：
  生成器顶部 `SHOW_NAMES = False`（或 `NAME_OPACITY` 调低）。
- 每个交叉点在 SVG 里都有透明热区 `<circle id="wei-f5-r1" data-player data-file data-rank>`，
  点击时由 `getScreenCTM().inverse()` 换算到 SVG 坐标；合法落点由服务端返回。
- 客户端按房间码和递增 `version` 采纳快照；同一房间内晚到的旧快照不会覆盖当前回合。
- 字体栈：`Noto Serif CJK SC / Source Han Serif / Songti SC / SimSun / Microsoft YaHei`。

## 7. 部署方案

完整步骤见 [deployment.md](deployment.md)。设计取舍：

- **不用 Docker**：一个 Node 进程即可承载全部房间（实测常驻内存约 25 MB），
  账号、会话、落座和进行中对局写入内置 `node:sqlite`（默认 `data/sanguo.db`），服务重启后自动恢复；
  由 systemd 托管，nginx 反向代理并终结 TLS。
- **Node 版本**：需要内置 `node:sqlite`，即 Node >= 22.5（根目录 `package.json` 声明 >= 22.6）。
- **WebSocket**：服务端同时支持 WebSocket 与 HTTP 长轮询。客户端目前固定使用长轮询
  （`transports: ['polling']`）——部分 CDN（如开启代理的 Cloudflare）会拒绝 WebSocket 升级；
  回合制棋类每步间隔数十秒，长轮询的延迟差异感知不到。直连源站部署时可改回 WebSocket。
- **静态资源缓存**：前端资源带 `?v=` 版本号，可放心缓存；发版时统一更新版本号。
